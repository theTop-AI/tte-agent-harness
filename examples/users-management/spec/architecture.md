# Users management — architecture

Feature id: `users-management` · Requirements: `requirements.md` · Status: approved (example only)

> Illustrative example: the files cited exist on `origin/main` as of 2026-11-12; the components
> marked "new" do not.

## Context

- **tte-engine** serves `/api/v1` as a FastAPI sub-app (`src/contextbank/server/api/__init__.py`,
  `API_PREFIX = "/api/v1"`, routers registered in `ROUTERS`). Every payload is an `Envelope` of
  `data` plus `meta` with `freshness` (`server/api/schemas.py`); errors are
  `{"error": {code, message, param}}` (`server/api/errors.py`, raised as `ApiError` from
  `server/api/deps.py`). The admin gate is `require_admin` (`deps.py`). Lists page with an opaque
  keyset cursor and `limit: int = Query(50, ge=1, le=200)`, answering `next_cursor` only on a full
  page and 400 `bad_param` for a cursor the route did not issue (`server/api/identity.py`,
  `/identity/principals`). The committed contract is `openapi.json`, regenerated by
  `scripts/export_openapi.py` and checked in CI with `--check`.
- **tte-frontend** reaches the engine only through `packages/api-engine`: a pinned
  `contract/openapi.json`, generated zod models under `src/generated/`, and a three-file domain
  shape (`contracts/`, `sdk/`, `query/`). A feature lives in `apps/web/src/features/<domain>/`
  (`api.ts` with server functions, `screens/`, `components/`, `index.ts`;
  `docs/architecture/apps-web.md` §4) and a route under `apps/web/src/routes/_authed/_app/`. The
  e2e suite runs against `@tte/mock-engine`, which answers every operation of the pinned contract
  from fixtures (`packages/mock-engine/README.md`).
- Prior art found by the analysis: the People screen (`features/identity`, `PeopleTable.tsx`) lists
  AI-tool users from `/identity/principals`. Panel members are a different set; the design keeps
  them apart.

## Interfaces

The panel's server function calls `GET /api/v1/users` with the session's own access token
(`engineForRequest()`, tte-frontend ADR-0002); the engine checks `require_admin` and scopes every
read to `deps.org_id`. The payload is specified in `api-contract.md`.

## Data

Members come from the organization's WorkOS memberships the engine already mirrors for its admin
gate. Read-only; no migration beyond an index for search. Scoped by `org_id` on every query.

## Decisions

- **D1** — A new `/users` operation rather than extending `/identity/principals`. Options: extend
  principals with a `kind=member`; new route · Because: principals are AI-tool users with rings and
  seats; members are panel identities with roles — one list with both would mislead.
- **D2** — Keyset cursor, `limit` 1–200 default 50 · Because: the engine's existing list routes do
  exactly this.
- **D3** — Frontend builds against the approved contract through the mock engine, before the engine
  release exists · Because: it lets FE and BE run in parallel; the pinned-contract bump is the
  integration step.

## Security and isolation

`require_admin` on the route; `org_id` in every `WHERE`; an id of another org is simply absent. The
response schema has no credential and no content field; the engine's schema test forbids content
fields globally.

## Failure modes

Database unavailable → the route answers the envelope with `freshness.state = absent` and a reason,
as `/identity/principals` does; the screen shows its error state with retry.

## Delivery shape

Wave 1 runs four tasks in parallel: engine API, engine tests (test-first), frontend screen (against
the mock engine), frontend tests. Wave 2 reviews each repository independently. Wave 3 integrates:
the engine change merges and releases first, the frontend bumps its pinned contract to that release,
and both pull requests are opened for a person to merge. Detail: `../plan.yaml`.
